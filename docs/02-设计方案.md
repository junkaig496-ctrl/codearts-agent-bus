# 02 · 设计方案

## 一、设计目标与非目标

**目标**

1. 让码道的多个会话（以及它们各自的智能体）能**互相发现、收发消息、派发与回执任务**。
2. 通过官方扩展点（**MCP + 技能**）实现，**零侵入**：不改码道、不装第三方依赖、删除配置即恢复。
3. 单机、单用户、离线可用；出故障要能自愈，不能把码道拖死。
4. 产物要能被**演示**（一眼看懂多个会话在协作）。

**非目标**

* 不做跨机器集群调度（本地总线已够本次场景；HTTP 通道只用于本机网络内接入 Space/远程）。
* 不做权限沙箱（码道自身已有沙箱与审批；总线只负责通信与任务编排）。
* 不替代官方的 AgentTeam（Space 模式的多智能体），而是**把协作能力带到 IDE 模式**。

## 二、核心约束 → 架构推导

| 约束 | 推导出的设计 |
|---|---|
| 码道的 MCP 客户端会为**每个会话各自拉起一个 MCP 子进程** | 进程之间**没有共享内存**，共享状态必须落盘或走 socket |
| 不能依赖守护进程（学生机器上容易被杀、重启、端口占用） | 选**文件式共享状态**：`~/.codeartsdoer/agent-bus/`，无 daemon、无端口、崩溃自愈 |
| 多个进程可能同时读写同一份状态 | **跨进程文件锁 + 原子写 + append-only 日志**（见第四节） |
| 智能体只能"主动调用工具"，服务端**无法主动推消息** | 提供 `wait_seconds` **长轮询**！这是本设计最关键的一处取舍（见 3.4） |
| 码道 Space 模式/网页版拿不到本地进程 | 额外提供 `StreamableHTTP / SSE` 传输，同一套 `bus_core` 状态（见第五节） |

> 备选方案对比：一开始考虑过"守护进程 + Unix Domain Socket / 命名管道"（与泄露报告里的
> `to: "uds:/.../sock"` 更形似）。放弃原因：Windows 命名管道/ASIO 实现复杂度高、
> 引入端口与生命周期管理、崩溃后需重建连接；而总线要传的是**小体量文本消息与任务元数据**，
> 文件 + 锁完全够用，换来"挂掉就重启、不用清理"的鲁棒性。UDS 的**语义**（会话互发消息、
> 同伴发现）被完整保留，只是**实现载体**换成了更稳的文件层。

## 三、协议设计

### 3.1 身份（会话注册）

* `session_id = slug(name) + "-" + sha1(项目绝对路径)[:6]`
  → 同一个 `name` + 同一个项目 = **同一个身份**，所以重复调用 `bus_register` 只是刷新心跳，
  不会产生一堆"影子会话"（这是实测踩过的问题，已写进测试）。
* 心跳 `last_seen` + 状态 `state(idle|working|offline)`；超过 `ONLINE_TTL=90s` 未更新判为 offline。
* 自动兜底：如果智能体忘了注册，MCP 层用 `{项目名}-{pid%1000}` 自动注册一个身份，
  保证它不会卡在"未注册"错误上空转（技能里仍要求显式注册以获得稳定名字）。

### 3.2 消息

```jsonc
{
  "msg_id": "m_1a2b3c4d", "ts": 1770000000.0, "ts_iso": "2026-09-23 20:04:10",
  "from": "planner-680a4f", "from_name": "planner",
  "to": "worker-frontend-680a4f", "to_name": "worker-frontend",
  "kind": "note|question|status|context|task|task_report|task_failed|reply",
  "content": "…", "correlation_id": "t_9f8e7d6c", "reply_to": "m_…"
}
```

* 投递 = 向收件人 inbox **append 一行 JSONL**（自包含，读的时候不需要 join）。
* 已读 = 每会话一个**读游标**（`cursors.json`），`ack=true` 时才推进；
  `ack=false` 等价于 peek，不会把消息"读丢"。
* `correlation_id` 把"一次协作"串成线索：派活消息 → 回执消息都带同一个任务号。

### 3.3 任务状态机（事件流 + 租约）

任务**不存最终状态**，只追加事件到 `tasks.jsonl`，读取时**折叠**成当前状态：

```
dispatch ──► pending ──claim──► running ──report──► done / failed
                 ▲                   │
                 └──── lease_expired ┘      （租约超时自动退回，防"领了不干"）
```

| 事件 | 触发 | 关键字段 |
|---|---|---|
| `dispatch` | leader 派活 | title / instructions / to / priority / timeout_seconds / artifacts |
| `claim` | worker 领活 | by / status=running |
| `progress` | 中途上报 | note / percent（同时刷新租约基准时间） |
| `report` | 回执 | status=done/failed/cancelled / result / artifacts → **自动通知派发方** |
| `lease_expired` | 系统回收 | 超时任务退回 pending，任何人可再领 |
| `cancel` | 撤单 | 理由写入 result |

* 事件流的好处：**审计与复盘天然有据**（`bus_log` 直接读它），也避免了并发下的写覆盖。
* 公共池：`to` 留空 → 谁先 `bus_next_task` 谁领；`priority=high` 排前面。

### 3.4 为什么必须长轮询（本项目最关键的设计取舍）

MCP 的工具是**被智能体调用**才执行的，服务端**没有任何办法主动告诉模型"有新消息了"**。
如果只提供"取一次就返回"的 `bus_inbox`，worker 只能靠模型自己反复轮询 —— 而模型一旦停下来等，
就再也不会调用工具，于是**任务永远送不到**。

解决方式：`bus_inbox(wait_seconds=N)` / `bus_next_task(wait_seconds=N)` 在服务端**阻塞轮询文件**，
最多等 N 秒才返回。这样"待命"就变成了**一次工具调用**，模型天然愿意做。
技能（SKILL.md）里把这条写成了硬性姿势：**worker 待命用 `wait_seconds=60`**。

配套的防呆：`wait_seconds` 建议 30~120；单次调用不返回空转死循环（返回值里带 `hint` 引导下一步）。

## 四、一致性设计（并发正确性）

| 机制 | 做法 | 为什么 |
|---|---|---|
| 跨进程互斥 | 单个 `bus.lock` 文件；Windows 用 `msvcrt.locking`、类 Unix 用 `fcntl.flock` | 一个锁文件便于审计，且不依赖端口 |
| **锁可重入** | 线程局部深度计数：同线程嵌套加锁只记深度，不再开新句柄 | **Windows 强制锁下，同进程用不同句柄锁同一字节会被自己挡住** → 曾导致 `dispatch → touch` 自杀式死锁（测试抓出） |
| 原子写 | 写临时文件 + `fsync` + `os.replace` | 避免读到半个 JSON |
| 追加日志 | inbox / tasks / events 全部 append-only | 写冲突最小化，天然可回溯 |
| 读游标 | 单独存，读时带容错 | 一行坏掉不影响整体（`_read_jsonl` 跳过坏行） |
| 并发实测 | 6 个进程同时派活/发消息 | 结果：任务 6/6、消息 12/12，**无丢失无重复** |

## 五、传输层

| 传输 | 文件 | 适用 | 要点 |
|---|---|---|---|
| **stdio** | `bus_mcp.py` | 码道 IDE / CLI / VS Code 插件 / JetBrains 插件 | MCP stdio 帧格式是**每行一个 JSON**（不是 Content-Length）；手写 JSON-RPC 2.0，实现 `initialize` / `tools/list` / `tools/call` / `ping` / 通知，未知方法回 `-32601`；**必填参数在协议层校验**，缺参数返回 `isError` 并给出可执行的修复提示 |
| **StreamableHTTP / SSE** | `bus_http.py` | 码道 Space 模式、网页版、远程 | 默认只监听 `127.0.0.1`；除 `/health` 外**强制 token**（首次启动自动生成并落盘）；额外暴露 `GET /dashboard`、`GET /ps` 便于远程看板；复用 `bus_mcp` 的协议层（把 `_send` 截流收集响应），避免两套实现漂移 |

## 六、安全边界（明确声明）

* 总线**只传数据**：消息与任务元数据。它**不执行**任何来自对端的代码或命令，不是远程执行通道。
* 本地模式（stdio）不开放任何网络端口。
* HTTP 模式默认 `127.0.0.1`，强制 token；如需局域网访问，需自行改 `--host` 并评估风险。
* 状态目录位于用户私有目录 `~/.codeartsdoer/agent-bus`，沿用码道自己的 `.codeartsdoer` 约定。
* 与码道自身的沙箱、审批、权限体系**正交**：本服务不绕过、不削弱它们。

## 十、协作实证：码道的智能体在实现过程中找出的 2 个问题

本项目在开发后期做了一个"反哺"验证：**让码道自己的智能体通过本总线领活**，
任务是"为 `bus_core.py` 写标准库 unittest 单元测试"。它产出了 248 行 / 5 个 TestCase / 12 个用例，
其中两个用例在**我独立复跑**时失败 —— 而这两个失败都是真问题，不是它的误报：

### 10.1 原子写在 Windows 上的替换竞争（真 bug，已修）

* 现象：并发场景下 `os.replace(tmp, registry.json)` 抛 `PermissionError(13, '拒绝访问。')`。
* 根因：Windows 的文件替换不允许目标文件此刻被任何句柄打开；而读侧（`_read_json`）与写侧
  可能来自不同线程/进程，天然存在"正在读 → 正好被替换"的窗口。POSIX 上 `rename` 是原子的、
  不 care 打开句柄，所以这类问题**只在 Windows 暴露**，我原有的"6 进程并发"测试没覆盖到这个时序。
* 修法：`_write_json_atomic` 对 `os.replace` 做**退避重试**（最多 3s，20ms 步长，超时转 `BusError`）；
  `_read_json` 同样对 `PermissionError` 短暂重试（最多 2s）后回退默认值。
* 回归保护：`tests/test_e2e.py` 新增 **[4] 同进程并发读写** —— 4 个读线程（`ps` / `list_tasks` /
  `log` / `list_peers`）与 4 个写线程（注册 + 派活）同时压，任何未捕获异常即失败。

### 10.2 只读视图的写副作用（设计瑕疵，已修）

* 现象：先 `list_tasks()` 再 `next_task()`，后者返回的 `reclaimed` 列表是空的。
* 根因：`list_tasks()` 内部调用了 `_reclaim_leases()` —— 一个"查看"动作把租约回收**执行并消费**了。
  读操作产生写副作用，既违反直觉，也让调用方再也拿不到那次回收的记录。
* 修法：抽出纯判断 `_lease_expired(t, ts)`；`list_tasks` 只把它**显示为** `pending` 并附
  `lease_expired=true` 标记（纯读、不写盘），真正的回收只发生在写路径 `next_task` 里。
* 这条修正同时让"看板刷新会偷偷改状态"的隐患消失。

### 10.3 这件事对本项目意味着什么

1. **能力是真的**：不是"我模拟了一个会话"，而是华为的智能体真的注册进来、领活、产出文件。
2. **它产生了正向工程价值**：找出的两个问题分别属于"平台相关并发正确性"与"API 设计纯度"，
   两者都已修复并加了回归测试；修复后它的 13 个用例全部通过。
3. **闭环可复现**：`docs/04-演示脚本.md` 第六节给了完整台词，任何人都能重放一遍。
