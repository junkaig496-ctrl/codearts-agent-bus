# 04 · 演示脚本（评审 / 录屏 / 答辩通用）

目标：**让看的人当场相信"码道里两个会话真的在互相派活、回传、汇总"** —— 这是本项目最有冲击力的 30 秒。

---

## 一、演示前的准备（约 5 分钟）

```bash
# 1) 重置总线，保证画面干净
python src/bus_cli.py reset --yes

# 2) 先各自跑一遍，确认环境没问题（这一步是保险绳）
python tests/test_e2e.py

# 3) 打开看板（会一直自动刷新，适合放第二个显示器/投屏副屏）
python src/bus_cli.py dashboard --open
```

码道里开两个会话：

| 会话 | 角色 | 对话框里先说的第一句 |
|---|---|---|
| 会话 A | leader（调度者） | `调用 bus_register，名字 planner，角色 leader，能力写"需求拆解/验收/汇总"` |
| 会话 B | worker（执行者） | `调用 bus_register，名字 worker-frontend，角色 worker，能力写"HTML/CSS 实现"` |

> 两个会话都收到 `session_id` 就说明通了（`planner-xxxxxx` / `worker-frontend-xxxxxx`）。

**如果码道多会话不顺**：会话 B 位置改用终端即可，效果一样（总线不关心对端是哪种会话）：

```bash
python src/bus_cli.py --as worker-frontend register worker-frontend --role worker
python src/bus_cli.py --as worker-frontend next -w 60      # 待命领活
```

## 二、正式演示（照抄台词，全程约 2 分钟）

### 第 1 幕｜先让评审看到"现在是聋哑状态"（15 秒）

在**会话 A** 里发：

> 你知道会话 B 现在在干什么吗？你能给它发消息吗？

（会话 A 只能回答"不知道、发不了" —— 这就是码道当前的能力边界。**这一幕是为了给第 2 幕立靶子**，
如果时间紧可以跳过。）

### 第 2 幕｜派活（20 秒）

在**会话 A** 里发这一整段：

> 使用 agent-bus 技能：用总线把「做一个项目首页」拆成两个子任务，分别派给 worker-frontend
> 和 worker-docs，priority 用 high，写清验收标准和允许改动的文件；派完用 bus_list_tasks 给我看板。

预期：会话 A 依次调用 `bus_register`（已注册则跳过）→ `bus_list_peers` → `bus_dispatch` ×2 →
`bus_list_tasks`。

**此时把看板切到前台**：会话拓扑里出现 2 个节点，任务看板出现 2 行 `pending`。

### 第 3 幕｜worker 领活并执行（30 秒，最精彩的一段）

在**会话 B** 里发：

> 使用 agent-bus 技能：去总线上领活并完成它，过程中用 bus_progress 上报进度，完成后用 bus_report 回执。

预期对话流（评审会亲眼看到工具调用）：

```
bus_next_task()            → 领到 t_xxxx「实现 index.html 首页骨架」
bus_progress(..., 30%)     → 已上报
bus_report(status="done", result="index.html 已生成…", artifacts="index.html")
```

**看板同步变化**：任务行从 `pending` → `running` → `done`，消息流里出现
`planner → worker-frontend 【新任务 …】` 与 `worker-frontend → planner 【任务回执 …】`。

### 第 4 幕｜收口（20 秒）

回到**会话 A** 发：

> 用 bus_inbox 收一下回执，然后用 bus_list_tasks 汇总所有子任务的结果和产物路径，给我一份汇总。

预期：会话 A 汇总出"哪个子任务完成、产物在哪、有没有没回执的"。

### 第 5 幕｜收尾（10 秒）

在**会话 A** 发：

> 生成协作看板。

（`bus_dashboard()` → 打印 HTML 路径；双击打开即可全屏展示，看板每 5 秒自动刷新。）

**演示结束语建议**：

> 码道官方支持多会话并行，但会话之间没有通信通道。agent-bus 用官方支持的 MCP + 技能扩展点，
> 把"并行"升级成"协作"：拆解、派发、领活、回执、汇总，全流程可视。全程没有修改码道一行代码。

## 四、常见翻车与应急预案

| 翻车 | 原因 | 应急 |
|---|---|---|
| 会话 B 说"暂无待领任务" | 任务派给了别的名字，或没在待命 | 让会话 A 用 `bus_list_peers` 报出准确名字重新 `bus_dispatch`；让会话 B 用 `bus_next_task(wait_seconds=60)` |
| 会话 A 收不到回执 | leader 没主动取信（**MCP 不会推消息**） | 让会话 A 发 `bus_inbox(wait_seconds=60)`；或直接用 `bus_list_tasks` 看状态 |
| 智能体把任务自己干完了 | 模型抢活 | 明确说："你是 leader，只负责拆解与汇总，不要自己实现" |
| 两个会话同名 | 都用了默认名 | 让它们 `bus_register` 用不同名字 |
| 画面乱（上一轮数据还在） | 忘了重置 | 演示前必跑 `python src/bus_cli.py reset --yes` |
| 时间极度紧张 | — | 直接跑 `python src/bus_cli.py demo`，一条命令演完整个剧本（不依赖码道，100% 可复现） |

**保底方案**：`python src/bus_cli.py demo --fast` —— 12 步剧本一次跑完并生成看板。
它的存在就是为了"无论现场什么状况，演示都不至于开天窗"。

## 六、进阶演示：把华为自己的智能体拉进来（实录台词）

这一段比"两个会话互发消息"更有说服力 —— **让码道自己的智能体当 worker，通过总线承担真实开发任务**。
2026-09-23 实测通过的完整台词如下（可直接照抄）。

**准备**：码道 IDE 打开本项目目录（`.codeartsdoer/mcp/mcp_settings.json` 已配好 agent-bus），
终端另开一个窗口扮演调度者：

```bash
python src/bus_cli.py register planner --role leader
python src/bus_cli.py ps          # 应能看到码道的 worker 已经注册（如果它已注册过）
```

**第 1 步｜让码道的会话报名上总线**（在码道聊天框里发）：

> 调用 bus_register 工具，name 填 codearts-worker，role 填 worker，capabilities 填「HTML/CSS 与 Python 代码实现」。然后调用 bus_list_peers 看看总线上现在有谁在线。

**第 2 步｜派一个真实任务给它**（终端）：

```bash
python src/bus_cli.py dispatch "用 unittest 为 bus_core 写单元测试"   "在 tests/ 下新建 test_bus_core_unit.py，用标准库 unittest 覆盖：注册幂等 / 已读游标 / 任务状态机 / 租约回收 / 原子写；每例用独立临时 AGENT_BUS_HOME；完成后实际运行 python -m unittest 跑通并贴真实回显。"   --to codearts-worker --priority high
```

**第 3 步｜让它领活（在码道聊天框里发）**：

> 使用 agent-bus 技能：现在请调用 bus_next_task 领取总线上分配给你的高优先级任务（wait_seconds 填 10）。领到后请真正动手完成——按说明实际创建文件、实际运行验证，过程中用 bus_progress 上报进度，最后用 bus_report 提交回执，并把真实回显写进回执的 result 里。

**第 4 步｜在终端盯总线（这就是演示画面）**：

```bash
python src/bus_cli.py ps
python src/bus_cli.py log -n 20
python src/bus_cli.py dashboard --open
```

你会依次看到：`register`（它报名）→ `dispatch`（你派活）→ **`claim`（它真的领走了）** →
`progress`（它一边干一边上报）→ 产物文件出现在 `tests/` 下。

**实测结果（可直接写进汇报）**：

* 码道智能体确实 `claim` 了任务，并三次 `bus_progress` 上报（"精读源码" → "设计 5 个 TestCase" → "测试文件已写 248 行"）；
* 它产出的 `tests/test_bus_core_unit.py`（13 个用例）**暴露了本项目的 2 个真问题**（Windows 原子写竞争、只读视图写副作用）；
* 修复后我独立复跑：`Ran 13 tests … OK` —— **它的测试成为本项目的回归资产**。

> 诚实备注：该子任务的 `bus_report` 回执照未提交（其租约已超时），所以在总线上它显示为"待收尾"。
> 演示时若要展示完整闭环，可在第 3 步末尾补一句："完成后务必调用 bus_report，status=done"。
